# ADR 0006 · 知识库服务的独立拆分时机

- 状态:已接受
- 日期:2026-09-06
- 背景:AgentPlatform 与 SwiftShip 为平行项目,共用同一知识库资产(设计 008 §11.3)。

## 决策

**现在不把知识库剥离为独立项目,采用"逻辑收口、物理不拆"(方案 A);拆分由明确的触发条件启动,而非提前布局。**

## 理由

- 平行的产品关系由**接口边界**保证,不靠进程/仓库隔离:消费方只见 REST(鉴权方案 A 用户 token 绑定,008 §11.3),实现位置对它们不可见;
- 知识库与平台账号体系(users/roles)、注册表(kb:<slug>,ADR 0005)、embedding 端点密钥管理紧耦合,现在剥离需重做鉴权与跨项目联动,在仅两个消费方的阶段无收益;
- 模块边界已清晰(`core/kb/*` + `api/kb.py` + retriever 抽象),随时可低成本外迁。

## 拆分触发条件(出现任一即启动方案 B:独立仓库 + 独立服务)

1. 第三方消费方接入,平台账号/权限模型开始束缚接入方;
2. SwiftShip 要求与平台**独立部署与可用性隔离**(平台故障不得影响其知识库);
3. 两项目账号体系分家,token 绑定方案失效(可先以 OIDC 互通过渡);
4. 检索规模/性能需求与平台主业务显著分化。

## 后果

- 短期:零迁移成本;知识库能力随平台发版;
- 长期:若触发条件到达,按"已服务化的模块外迁"执行,消费方接口不变;
- 约束:对 `core/kb` 的改动不得引入与平台非知识库模块的新耦合(现有耦合清单:auth、registry、llm/embeddings)。
