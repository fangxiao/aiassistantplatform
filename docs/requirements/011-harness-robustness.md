# 需求文档 · Agent Harness 加固(M21 · Loop Robustness)

- 文档版本:v0.1(草案,待评审)
- 日期:2026-09-29
- 流程阶段:阶段 1 · 需求
- 决策记录:2026-09-29 用户确认走「自研加固」路线(不引入成熟框架重写 runtime);
  骨架保持现有事件流架构,按本文档四个工作流逐项加固。

---

## 1. 问题陈述

数日实际使用表明,平台 agent 运行时(harness)在**多轮循环对话**中的稳定性明显
弱于成熟实现。故障并非孤立 bug,而是 loop 层的结构性短板,每次都以"线上事故 +
事后补丁"方式处理(20260926 表单三连崩、20260928 断流事故、DetachedInstanceError)。

基于代码证据的五项短板:

| # | 短板 | 现状证据 |
|---|---|---|
| H1 | 无流式断线恢复 | LLM SSE 中断即整轮作废;无检查点/续跑;前端只能提示"[连接中断]"由用户手动重试 |
| H2 | 手搓并发模型 | `stream_agent` 单函数 1192 行,内嵌 2 个轮询队列(0.05s/0.1s `wait_for`);嵌套 skill 流失败曾静默丢弃;ORM 属性在异步执行后被访问曾触发 DetachedInstanceError |
| H3 | 无上下文管理 | 多轮历史无压缩/截断策略;长会话 token 持续膨胀,变慢且易触发上游超限,形成恶性循环 |
| H4 | 错误处理靠事故驱动 | 无系统性错误分类(可重试/可降级/需人工);同类故障反复以补丁方式修复 |
| H5 | 工具调用双轨制 | native function calling 为主,文本兜底解析含截断启发式(`loop.py:867-900`),对模型输出格式极敏感,模型侧变化即崩 |

根因:loop 层为快速支撑功能迭代(22 控件、skill 流式、审批流、多模态)持续堆叠,
缺乏独立的稳定性设计。harness 是所有会话的公共底座,其稳定性短板会被**每一个**
插件与用户放大感知。

## 2. 目标

1. **断线可恢复**:LLM 流中断后,平台自动从检查点续跑,用户无感或最多一次可见的
   "自动重试"提示;不再要求用户手动重发消息;
2. **长会话可控**:多轮对话上下文有明确的压缩/截断策略,token 用量有上界保障,
   长会话不因历史膨胀而劣化或崩溃;
3. **并发结构可维护**:`stream_agent` 拆分为职责单一的模块,队列轮询改为事件协作,
   嵌套子调用的失败**必须**以结构化错误进入主循环(不允许静默);
4. **错误有分类**:运行时错误按"可重试/可降级/需人工"三类统一处理与上报,
   新故障类型出现时按分类落位,而不是逐个打补丁;
5. **文本兜底可收缩**:建立模型工具调用能力登记,原生 function calling 覆盖的
   端点不再走文本解析路径,兜底解析的触发面可观测、可收敛。

## 3. 用户故事

- **U1 断线自动续跑**:用户发送消息,agent 长回复中途 SSE 断开。前端短暂显示
  "连接中断,自动恢复中";平台从最近检查点(已确认事件流)继续执行并流式补齐剩余
  内容,用户看到回复完整呈现,无需任何手动操作。
- **U2 不可恢复时的明确交代**:上游持续故障超过重试预算。前端收到结构化错误事件,
  展示"第 N 轮回复中断,已保留已完成部分,点击重试从断点继续";点击后从检查点
  续跑,已完成部分不重复生成、不重复计费。
- **U3 长会话不劣化**:用户与同一会话对话 50+ 轮。平台按策略压缩早期历史
  (摘要/裁剪),回复质量与响应速度保持稳定;被压缩的事实用户可通过"查看上下文
  摘要"知情。
- **U4 子调用失败可见**:skill 嵌套调用失败。主循环收到结构化错误,回复中明确
  告知用户"该技能执行失败及原因",外层模型据此自纠或致歉;不出现无声停摆。
- **U5 运维可观测**:开发者/管理员在日志与 trace 中看到每轮的错误分类、重试次数、
  检查点位置、上下文压缩事件;故障排查不再依赖读源码。

## 4. 验收标准

- **A1(H1)**:在 LLM 流式传输中人为断开连接(注入故障),回复自动续跑完成,
  全程无用户操作;相同注入下"已完成部分不重复"。
- **A2(H1)**:持续故障场景,前端收到结构化错误事件(非裸 HTTP 错误),
  提供从断点重试的入口,重试后不重复计费已完成轮次。
- **A3(H3)**:50 轮会话 token 总量有可配置上界;压缩事件落 trace;
  压缩后关键事实(用户在早期轮次提供的约束)可通过摘要保留——用验收用例集验证。
- **A4(H2)**:`stream_agent` 拆分后单文件 ≤400 行;轮询队列清零(以事件/任务协作
  实现);故障注入测试覆盖"子调用失败""session 失效"两类历史事故场景,全部以
  结构化错误呈现。
- **A5(H4)**:错误分类枚举落库/落 trace;每类错误有明确的处理策略声明
  (重试预算/降级行为/上报渠道);新增错误的接入有文档化流程。
- **A6(H5)**:工具调用路径按模型能力分流并落 trace;文本兜底解析仅对登记为
  "无原生工具调用"的端点生效;兜底触发次数可统计。
- **A7(回归)**:既有全部会话级测试(表单、确认、控件渲染、多模态)通过;
  现有已注册插件(sharestudy/studyassistant/writewx/contract/prd-review-assistant)
  冒烟通过。

## 5. 非功能约束

1. **不引入新基础设施**:数据库/缓存/消息中间件不新增;检查点与错误记录落现有
   PostgreSQL,压缩用现有 LLM 通道;
2. **插件零感知**:本里程碑不改插件 SDK 契约,所有已部署插件无需重新发布;
3. **可灰度**:断线恢复与上下文压缩均可按会话/按模型灰度开关,可一键回退;
4. **成本可算**:上下文压缩本身消耗 token,压缩策略须将"压缩成本"纳入考量
   (压缩频率与收益可配置);
5. **不阻塞功能迭代**:加固以并行工作流推进,期间常规功能开发不受冻结。

## 6. 范围外(后续里程碑)

- 引入成熟 agent 框架重写 runtime(已决策不做);
- 前端渲染层稳定性(如 admin 页死循环类问题,另立专项);
- 多模型并行的 speculative execution / 投票等高级可靠性机制;
- 插件沙箱隔离与资源配额(属插件平台安全专项)。

## 7. 分期建议

| 期 | 内容 | 理由 |
