## 1. 背景与目标

### 1.1 背景
当前平台的助手能力来自插件(skill + tool),但助手的"知识"只能来自开发者写死在 prompt 里的内容,或用户在对话中临时粘贴。用户没有地方沉淀自己的私有文档知识,插件也无法复用一份权威的领域文档(产品手册、规章、FAQ)。同时,平台的注册表机制已验证「资源化 + 显式依赖 + SemVer 复用」的心智,知识库是这一心智的自然延伸:**知识库即资源**。

### 1.2 目标
- 终端用户可上传文档形成**个人知识库**,对话时助手自动检索引用,无需改插件;
- 平台可运营**公共知识库**,进入 registry,插件像依赖 `tool:pdf_parse@^1.0` 一样以 `kb:<name>@<version>` 依赖;
- 插件开发者**零 RAG 实现**:检索由平台内置 `tool:kb_search` 收口,插件只在需要时显式调用;
- 检索结果**可溯源**(文档名 + 原文位置),为后续引用组件打基础。

### 1.3 非目标(明确不做)
- 不做通用文档协同编辑(不是飞书文档);
- MVP 不做文档级 ACL、shared 团队协作(二期);
- 不做多模态(图片/音频)检索,MVP 仅文本型文档;
- 不做对外互联网爬取,MVP 导入仅限手动上传(连接器二期+)。

## 2. 用户角色与用户故事

### 2.1 使用者(End User)
- **US-1 上传建库**:作为使用者,我想新建一个个人知识库并批量上传 md/pdf/txt 文件,看到每个文件的处理状态(排队/解析中/可检索/失败),以便知道何时可用。
- **US-2 会话挂载**:作为使用者,我在和助手对话时可以选择挂载哪些知识库(含公共库),助手回答涉及我的文档时自动引用,我无需复制粘贴内容。
- **US-3 溯源**:作为使用者,当助手基于知识库回答时,我能看到引用了哪篇文档的哪一段,以便核实。
- **US-4 管理文档**:作为使用者,我可以删除/替换库内文档,删除后立即不可再被检索到。

### 2.2 开发者(Developer)
- **US-5 静态依赖**:作为插件开发者,我在 `plugin.yaml` 声明 `depends_on: ["kb:product_docs@^1.0"]`,部署后该助手开箱即带这份公共知识,无需用户手动挂载。
- **US-6 显式检索**:作为插件开发者,我在 skill/tool 中调用平台内置 `tool:kb_search`,传入 query 与可选的库范围,拿到带溯源信息的片段列表。
- **US-7 浏览公共库**:作为开发者,我用 `agentplatform registry` 能看到公共知识库列表与版本,像查 tool 一样。

### 2.3 平台管理员(Operator)
- **US-8 运营公共库**:作为管理员,我可以创建/更新/下架公共知识库并发布版本;更新版本后依赖方按 SemVer 约束生效。
- **US-9 配额**:作为管理员,我可以设置单用户存储配额与文档数上限,防止滥用。

## 3. 功能需求

### F1 知识库管理
- F1.1 新建/重命名/删除个人知识库(private);管理员可新建公共库(public)。
- F1.2 文档上传:支持 md / txt / pdf(MVP);单文档 ≤ 20MB,单库文档数 ≤ 200(可配)。
- F1.3 处理 pipeline 异步执行:解析 → 切分 → 向量化;文档状态可见;失败可重试并展示原因。
- F1.4 删除文档为软删,检索层立即过滤。

### F2 检索
- F2.1 内置工具 `tool:kb_search(query, kb_ids?, top_k?)`:向量检索(MVP),返回片段列表,每条含 `kb_id / document_id / document_name / chunk_index / score / text / source_span`。
- F2.2 权限过滤在检索层强制:会话可检索范围 = 用户挂载的库 ∪ 插件静态依赖的公共库,且调用者必须有该库读权限。
- F2.3 溯源信息必须保留到结果(为三期引用组件做准备)。

### F3 挂载与注入
- F3.1 会话级挂载:用户在会话(或助手偏好设置)中选择挂载的个人库与公共库。
- F3.2 插件静态依赖:`plugin.yaml` 的 `depends_on` 支持 `kb:` 前缀资源,SemVer 约束语义与 skill/tool 一致(002 §8)。
- F3.3 检索由 agent 通过 function-calling 显式调用 `tool:kb_search` 触发,不做每请求强制 RAG;插件可在 skill prompt 中引导调用时机。
- F3.4 冲突处理:同一公共库多版本被依赖时按 SemVer 解析规则取唯一版本;用户挂载与插件依赖重叠时去重。

### F4 Registry 集成
- F4.1 公共知识库进入 `skill_tools` 同源注册体系(`id = kb:<name>`,`kind = kb`),`agentplatform registry` 可见。
- F4.2 CLI:`agentplatform registry` 列出公共库;`agentplatform validate` 校验 `kb:` 依赖存在性与版本约束。

### F5 WebUI
- F5.1 知识库管理页:库列表(个人 + 可见公共库)、新建、文档列表(状态/大小/操作)、检索测试框(输入 query 预览命中片段)。
- F5.2 会话内挂载入口:会话侧栏或设置中勾选库。

### F6 权限模型(库级)
- F6.1 private:仅 owner 可读写。
- F6.2 public:所有人可读;仅管理员可写(运营库)。
- F6.3 shared 协作(成员/角色)为二期,数据模型预留字段不做功能。

## 4. 非功能约束
- **NFR-1 性能**:`kb_search` P95 ≤ 800ms(单库 ≤ 5 万 chunk 规模);文档上传到可检索 ≤ 60s(1MB 文本类)。
- **NFR-2 隔离**:向量数据按 kb 隔离过滤,任何检索请求不得跨权限泄露片段。
- **NFR-3 扩展**:检索接口在 `core/kb/` 收口,pgvector 实现为默认后端,可替换为独立向量库而不改上层 API。
- **NFR-4 依赖边界**:不新增插件侧依赖;embedding 服务复用 `llm_endpoints` 机制(新增端点类型)。
- **NFR-5 兼容**:不改变现有消息信封与 22 组件;溯源组件为三期新增,不破坏现有渲染。

## 5. 验收标准(核心闭环)
1. 用户上传一份 md 到个人库 → 状态变为「可检索」→ 会话挂载后提问文档内容,助手调用 `tool:kb_search` 并给出带文档名的回答;
2. 插件声明 `kb:demo_docs@^1.0` → `agentplatform validate` 通过 → 部署后新会话不手动挂载即可检索到该库内容;
3. 未挂载库的会话中,`kb_search` 仅能命中公共库;用户 A 无法检索用户 B 的 private 库(接口层直接拒绝);
4. 删除文档后再次检索不再命中;
5. `agentplatform registry` 输出包含 `kb:` 类型资源。
